Burn owner and payload

The burn script R

Section titled “The burn script R”

A burn owner is the P2SH hash of a short script R that names the payout:

Bytes Value Meaning
1 6a OP_RETURN: the script fails as soon as it runs
1 0f Push the next 15 bytes
15 kUSDT/redeem/v1 Tag (ASCII)
1 01 Push the next byte
1 01 or 02 Chain code: Ethereum or BNB Chain
1 14 Push the next 20 bytes
20 address The EVM address to pay

R is always 40 bytes.

Why it works

Section titled “Why it works”
  • Nobody can spend it. A p2sh owner approves only through an input whose redeem script is exactly R. R starts with OP_RETURN, so that input always fails. Tokens sent to a burn owner can never move again.
  • Nobody can redirect it. The payout chain and address are inside R, and R is fixed by the hash in the token state. A signer checks that a Release names exactly that chain and address.
  • Nobody can borrow into it. The burn state must use borrow scheme 0x00, with a zero borrow guard and a zero extension commitment. Otherwise a third party could recreate it at a new outpoint with one more unit, which would look like a second burn. Signers refuse any other burn state, and its kUSDT is lost.

The redemption payload

Section titled “The redemption payload”

A Kaspa transaction has a free payload field. A redemption transaction should carry the preimages of its burn owners there, so the bridge can find and check them:

Bytes Value Meaning
5 KUSDT Magic (ASCII, upper case)
1 01 Payload kind: redemption
1 count Number of burn outputs described, 1 to 255
22 × count entries For each: output index (1 byte), chain code (1 byte), EVM address (20 bytes)

A missing payload

Section titled “A missing payload”

The payload is a convenience, not a requirement. If a burn has no payload, or the payload is wrong, anyone can later give the coordinator the preimage: the transaction ID, output index, chain and address. The coordinator checks it against the burn owner. The coordinator API accepts it on POST /redeems.

Note

The tag in R is kUSDT/redeem/v1 (mixed case). The tag in the EVM redeem ID is kusdt/redeem/v1 (lower case), and the payload magic is KUSDT. All three are exact byte strings; do not normalise them.
