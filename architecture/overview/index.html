Architecture overview

kUSDT has parts on three kinds of system: smart contracts on two EVM chains, covenants on Kaspa L1, and off-chain services run by the bridge operators. The user’s apps sit on the user’s device.

  1. Deposit. A user deposits USDT into a vault, from the web app or any EVM wallet.
  2. Read. Each of the 5 signers reads vault events and Kaspa state from its own nodes.
  3. Sign. Signers send their signatures to the coordinator.
  4. Mint. The coordinator submits mint transactions to BridgeMint on Kaspa.
  5. Release and refund. The coordinator submits release and refund transactions to the vaults.
  6. Use kUSDT. Users send kUSDT, swap in KasPool, add liquidity and burn to redeem, all as Kaspa L1 transactions.
  7. Pause. The monitor checks backing against supply, mints against deposits and releases against burns, from its own nodes. The guardian key can pause both vaults and BridgeMint, and do nothing else.
  8. Configure. The vault owner sets each vault’s parameters within hard bounds, its signer set and its guardian.
  9. Status. The coordinator serves status to the web app.

Design choices

Section titled “Design choices”
  • Kaspa L1 only. Every Kaspa-side rule runs in Kaspa’s script engine. See Kaspa L1, not a layer 2.
  • A federation, rate-limited on both sides. Kaspa nodes cannot verify Ethereum or BNB Chain, so 5 signers attest to deposits and burns. Both sides cap what a bad quorum could move per day. Zero-knowledge light-client verification is the planned upgrade, not part of v1.
  • The coordinator is not trusted. Each signer checks every request against its own nodes. Anyone may submit a correctly signed mint or release.
  • The payout is fixed at burn time. A burn commits to the payout chain and address, so a release cannot be redirected.
  • Standard token code. kUSDT’s KCC20 actor is the unmodified reference, so existing KCC-20 wallets and indexers work with it.
